# ADR-002: Adopt a Modular Monolith Architecture

## Status
Accepted

## Context
FoodHub was initially implemented with controllers registered directly
in the root AppModule. As the application grows, this structure can
make responsibilities harder to organize and maintain.

We need to separate application features while keeping the application
within a single deployable NestJS application.

## Decision
We decided to adopt a modular monolith architecture using NestJS modules.

The application is divided into feature modules:

- CatalogModule: manages restaurant-related functionality.
- OrderingModule: manages order creation, retrieval, and status changes.
- AppModule: imports the feature modules and keeps authentication.

Each module owns its controllers, services, and repositories.

OrderingModule communicates with CatalogModule through the exported
CatalogService rather than accessing CatalogRepository directly.

Order persistence is accessed through an OrderRepository interface,
with InMemoryOrderRepository as its current implementation.

## Consequences

### Positive
- Clear separation of responsibilities.
- Better encapsulation between modules.
- Easier maintenance and future extension.
- Repository implementations can be replaced without rewriting
  business logic.
- Business rules are kept inside services instead of controllers.

### Negative
- More files and module configuration.
- Developers must understand dependency injection and module boundaries.
- Cross-module communication requires deliberate interface design.

### Future Considerations
- Replace in-memory order storage with a database-backed repository.
- Add Payment, Delivery, and Notification modules when required.
- Define event-based communication for workflows involving multiple modules.
